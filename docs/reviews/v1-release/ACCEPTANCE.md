# Acceptance gates and regression protocol

These are proposed release criteria for the pinned v1 candidate. Record a pass only with the actual build SHA, dataset version, environment, reviewer, time and attached evidence. A missing denominator or unsigned product rule leaves its gate open. The fixture file contains 23 synthetic specifications with setup, actions and observable expectations. It has no connection configuration. No feature earns a pass from validating the fixture file.

## Running the specifications

Load only the synthetic [fixture vectors](fixtures.json). Bind actions to the supported mobile/API entry points on a disposable stack. Where an adapter or route is absent, record **blocked**. For each case record setup hash, actor, initial state, input, user-visible result, server-persisted result, negative assertions and cleanup. Run retryable cases twice and under concurrent delivery. Compare against an independently computed oracle, including counts, score and ownership. A mock can qualify deterministic handling; a live-provider, hosted or physical-device gate needs its own evidence.

Keep the web prototype running while evidence is collected. Record the candidate SHA and signed inventory hash for any retest. Protect raw device and provider evidence from learner data, and retain only sanitized synthetic evidence in QA.
