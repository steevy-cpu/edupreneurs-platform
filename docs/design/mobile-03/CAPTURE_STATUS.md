# Mobile-03 visual capture status

This file tracks evidence and gaps; it is not an acceptance report. The foundation is `4abb2e241c9909aee7c191d05b70307f851eb154`. The first hosted workflow run is [45900762600](https://github.com/steevy-cpu/edupreneurs-platform/actions/runs/45900762600), triggered for candidate `fc59afab6ad7ccd394267a20f0514b464a62c169`. Both capture jobs failed at `01_sign_in_and_save` at all three font scales after successful builds; their small artifacts contain no screenshots. The first harness did not preserve sanitized failure details, so the immediate cause is not established. The retry adds credential-safe diagnostic categories. No capture from this run counts as visual evidence. A workflow file or a running job is not proof of successful device validation.

A separate local API 24 ARM emulator was created with 480×800 px, 240 dpi and 1024 MB RAM. A separate Supabase project `mobile03-visual-isolated` used API port 56421 and DB port 56422; the shared project was not reset. The hardened baseline mobile suite passed locally: 32 suites, 477 tests. TypeScript and the full mobile suites also passed in both hosted jobs on the first workflow run. The local baseline build was initially blocked waiting on a shared Gradle daemon; its client was interrupted and the build retried with a private Gradle cache. A denied sandbox ADB socket was resolved with host access. Earlier local dependency setup also failed on an incomplete offline cache before succeeding with the existing default cache.

The hosted workflow uses real screens via the repository's Maestro journeys, not Design-00 previews. It attempts the journeys at 1.0, 1.3 and 2.0 font scale and uploads original captures and a machine-readable manifest per build. Its current journey only exercises a subset of French and Haitian Creole states. Even if it passes, **the requested complete matrix is not satisfied**: it does not systematically capture each state in both languages, the selected-answer state, sign-in with the keyboard visible, a larger viewport, or explicit separate TalkBack behavior. Reduced motion is configured but has not been independently assessed. It also does not yet establish startup, memory, scrolling or actual device performance. Failure of any journey marks its captures as failed and excludes them from comparison sheets.

The `make-comparisons.py` utility only pairs captures with matching state, locale, font scale, viewport and flags from successful journeys. A separate comparison job runs only if both capture jobs succeed. It does not claim visual equivalence or accessibility conformance. Before release, manually inspect every image, extend coverage to the missing cells, verify credential-free artifacts, test TalkBack and keyboard visibility separately, and perform physical-device testing. No learning-screen changes should be characterized as device-verified until the actual images are reviewed.
