# 2. Harness, metrics and offline results

Code: `benchmarks/jude-02a/jude_eval/`. It reuses Jude-01's own lesson
contracts, retriever, prompt template (`jude-tutor.v1`), provider interface,
output validator and service, so a candidate is measured against exactly what
production would send and accept.

## Two layers

| | Model layer | Pipeline layer |
|---|---|---|
| Question | What does this model return for the prompt Jude would send? | What does a learner get, and what does it cost, with this model behind the whole service? |
| Calls | One per case, no retry | As the service decides (retries, short-circuits) |
| Scored | The raw reply | The response or error, provider calls, spend |
| Jude-01 screens | **Bypassed**, to see what the model does when a screen misses | Applied |
| Faults | None | Injected: timeout, outage, rate limit, bad credential, garbage, truncated JSON, empty, invented reference, wrong language, extra field |

Faults wrap *any* provider and damage its real answer, so the same failure
cases will run against a real model later.

Both layers build the prompt with the retrieval strategy recommended in
[03](03-cross-language-retrieval.md), so a model is not blamed for passages a
weak ranker failed to find. When retrieval still finds nothing, the model layer
supplies the gold blocks and records `context_source: gold` (27 of 203 cases).

Most of those 27 are cases where finding nothing is the *right* retrieval
result: 7 of the 8 unsupported-claim traps and 6 of the 10 boundary messages
match no passage, so in the real pipeline the learner gets the fixed "not in
this lesson" reply and no model is called. The model layer still puts them to
the model, to see what it would do if retrieval let them through.

## The nine measurements

Every rate is reported as passed/applicable. A metric only counts the cases it
applies to; "not applicable" is never shown as a pass.

| # | Asked for | Column(s) | How it is decided |
|---|---|---|---|
| 1 | Output-schema validity | **Schema valid**, **Accepted**, rejection reasons | Parses as the `ModelAnswer` contract; passes Jude-01's full validator (what a student could see); the validator's reason code when it does not |
| 2 | Lesson-reference correctness | **Refs issued**, **Gold cited**, precision | Every cited id was issued for this request; at least one cited block is one that answers the question |
| 3 | Grounding and unsupported claims | **No unsupported claim**; flag *novel numbers* | On trap cases: did it present as lesson content what the lesson does not say. Flag only: numbers in a lesson-grounded answer that occur nowhere in the passages or the question |
| 4 | Hint-level adherence | **Hint given**, **Result held back** | A hint request gets a hint; at levels 1–3 the final answer pattern is absent. Level 4 is left to humans |
| 5 | Language adherence | **Language declared**; flag *language suspect* | Declared language equals the requested one. The flag is Jude-01's marker-word heuristic: it fires only on strong evidence of the *other* language |
| 6 | Response completeness | **Complete**; flag *possibly truncated* | Required fields for the intent are present; output tokens reached the limit |
| 7 | Latency and token usage | median and p95 ms; mean input/output tokens | Clock around the provider call; provider-reported tokens |
| 8 | Cost per response | mean USD per response | Tokens × the candidate's price, rounded up per direction (Jude-01's `ModelPrice`) |
| 9 | Retry and failure behaviour | pipeline: cases passed, provider calls, spend | Outcome, exact number of calls and spend (`zero`, `positive`, `worst case`) for each injected fault |
| + | Injection, privacy | **No forbidden text** | An injected instruction's payload, the system-prompt canary, or a repeated private detail appears in the raw reply |

### Deliberately not scored by the harness

- **Whether the explanation is correct, clear, kind or pedagogically sound.**
- **Whether the Haitian Creole is authentic.** There is no Creole-quality score
  anywhere in the code. The single language signal is a warning that a reply
  looks like French instead.

Both go to people, with the rubrics in [07](07-human-review.md). The harness
also prints mean words per sentence for the "simple language" cases as a
descriptive number, not a grade.

## Candidates that can run offline

| Kind | What it is | What its scores mean |
|---|---|---|
| `mock` | Jude-01's deterministic mock, unchanged. Stitches lesson text; never abstains | The plumbing works |
| `simulated` | Six scripted profiles built on the mock, each with one defect | **Each metric separates good from bad behaviour.** They are not models and predict nothing about one |
| `live` | A real model | Never constructed in Jude-02A |

Reading it:

- Each scripted defect shows up on its own column (bold) and leaves the others alone.
- **`leaky-tutor` is fully *accepted* by Jude-01's validator while giving the
  answer away in every hint.** The validator cannot see a pedagogical failure;
  only the hint metric (and a human) can. This is the clearest argument for
  evaluating beyond "valid output".
- The plain mock scores 0/6 on unsupported claims because it always answers.
  That is the mock's nature, and a reminder that its other 100%s mean little.
- `slow-costly` is indistinguishable on quality and shows up only in latency
  (median 8.2 s vs 2.6 s, scripted) and cost (5×, scripted).

Pipeline layer: the mock and the reference profile pass 27 of 30 cases and all
12 provider-failure cases. The three that do not pass are the same for every
candidate and are findings about Jude-01, not about a model — see
[08](08-limitations-and-educator-checklist.md#findings-about-jude-01).

## Reproducibility

- Offline runs use a virtual clock and seeded, hash-based "randomness": the same
  commit produces byte-identical result files (`evaluate.py all --check`).
- Every result file states the prompt version, retrieval strategy and output limit.
- A live result file additionally records the model, price version, cap, who
  authorised it, spend and whether the run stopped early.

## Live evaluation (built, off, never run)

`evaluate.py live` is refused unless **all** of these hold; the refusal lists
every missing one:

1. `--live` was given;
2. `JUDE_EVAL_LIVE_AUTHORIZED` equals the phrase `I authorize paid model calls for Jude evaluation`;
3. a credential is in `JUDE_EVAL_OPENROUTER_API_KEY` — used by nothing else, and
   refused if it equals the application's `EDU_TUTOR_PROVIDER_API_KEY`;
4. `--model` names one model that has a price in `config/published_prices.json`
   read no more than 30 days ago;
5. `--max-spend-usd` is above 0 and at most 20 (a ceiling in code);
6. `--authorized-by` names a person, recorded in the result file.

The cap is enforced **before each call**: the worst case for that call (whole
input plus the full output limit) must still fit, or the run stops. A call that
fails is charged at its worst case. Requests ask OpenRouter for providers with
`data_collection: deny` and `zdr: true`. The key is read from the environment
only, is never written to a result file, and only the benchmark's synthetic
questions are sent. Tests cover every refusal, the cap, and the request body,
through an in-memory transport.

**Never run.** Unverified against the real API: whether the routing fields are
accepted as sent, and whether each model honours `response_format:
{"type": "json_object"}` — OpenRouter's structured-output page documents
`json_schema`, and says support is per endpoint. Check this on the first
authorised call; `extra_body` can carry a `json_schema` if needed.
