## 5. Native SQLite and SecureStore behaviour (iOS)

- **expo-sqlite** works through the app's adapter, including
  `withExclusiveTransactionAsync` (every answer and every sync acknowledgement
  uses it). Files live in the app sandbox under `Documents/SQLite/`; total size
  after the test: 356 KB.
- **Persistence**: data survived three force-quits.
- **expo-secure-store**: after a force-quit the app opened straight to the home
  screen with the backend down, so the session was read back from the Keychain
  without any network. After sign-out the app returned to the sign-in screen.
- **No token in SQLite**: zero JWT-shaped strings in the account database file.
  (The one value starting with `eyJ` is the opaque pull cursor, which is
  base64-encoded JSON, not a credential.)
- Not verified: Keychain behaviour across device restore/backup, or on a locked device.

## 6b. Follow-up session (same day)

- **"Simulator app did not open fast enough" (reported by the founder running
  `make mobile-ios`).** Cause: Xcode 26.6 was installed from an archive and had
  never been opened, so macOS did not know its Simulator app; `open -a Simulator`
  (what Expo runs) failed with "Unable to find application named 'Simulator'".
  Opening Simulator once by its full path registers it. `scripts/ios-open.sh`
  does that and launches the already-installed build without rebuilding.
- **Branding.** User-facing name changed to **Edupreneurs** (app text, header
  title, `app.json` display name). Screenshots `27`, `28`. Bundle id, Android
  package, deep-link scheme and Expo slug were left unchanged.
- **Session survives a device restart.** Sign in → shut the simulator down → boot
  → launch: the app opened on the home screen (flow `08_*`, screenshot `26`).
- **Unintended side effect, disclosed.** Re-applying the configuration after the
  rename (`expo prebuild` without `--clean`) regenerated the whole `ios/` folder
  because the project name changed. That deleted the generated Xcode project,
  `ios/Pods` and `ios/build` (about 3.8 GB, all regenerable). The app installed in
  the simulator was not affected and still runs, but its home-screen label still
  says "Mon Edupreneur" until the iOS app is rebuilt (about 15 minutes).
- **Observed once, not explained.** After the simulator had been shut down and
  booted, the app showed the sign-in screen instead of home. A deliberate
  sign-in → reboot → launch test afterwards passed, and changing the account's
  password on the server did not sign the app out. The cause of the single
  occurrence is unknown.

## 11. Test it yourself (iOS)

```bash
# once
make start                                   # backend stack (Docker)
make mobile-env TARGET=ios-sim

# terminal 1
make api

# terminal 2 — prints an e-mail and password for the synthetic student
make dev-login ACCOUNT=student_a

# terminal 3 — builds (first time ~10 min), boots a simulator, launches the app
make mobile-ios
```

Then follow "The manual acceptance test" in `apps/student-native/README.md`.
To cut the backend instead of using airplane mode: stop `make api` with Ctrl-C.

To replay the automated flows (simulator booted, app installed, Metro running).
Maestro is not committed; download `maestro.zip` from the project's GitHub
releases page and unzip it into `.tools/` at the repository root (needs Java):

```bash
cd apps/student-native/e2e
export DEVELOPER_DIR=/Applications/Xcode-26.6.app/Contents/Developer
../../../.tools/maestro/bin/maestro test -e EMAIL=student.a@edupreneur.test -e PASSWORD=<from dev-login> 01_sign_in_and_save.yaml
# stop the API, then:
../../../.tools/maestro/bin/maestro test 02_offline_quiz.yaml
../../../.tools/maestro/bin/maestro test 03_reopen_offline.yaml
# start the API again, then:
../../../.tools/maestro/bin/maestro test 04_reconnect_sync.yaml
```
